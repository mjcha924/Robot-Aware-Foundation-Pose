01 · 우리가 학습하려는 것

FoundationPose가 이미 이해하는 시각 정보에 로봇의 형상과 움직임을 보태, 물체가 가려지는 조작 과정에서 물체의 6D pose를 더 잘 추적할 수 있는지 시험한다.

6D pose는 위치 3자유도와 회전 3자유도다. 로봇의 행동을 생성하는 정책을 학습하는 프로젝트가 아니다. 현재 RGB-D와 pose hypothesis를 보고 물체 자세를 수정하는 refiner를 학습한다. 물체 CAD를 아는 model-based 조건이다.

2026-11-26~27에 RTX 5080에서 smoke, tiny, pilot·motion 3-seed, FK 감사와 CAD-only 대조를 실제로 실행했다. 실행 중 발견한 회전 부호·dtype·float32 누적 오차 문제는 수정했다. 측정 결과와 그 한계는 27절과 docs/OMY_5080_RESULTS.md, docs/OMY_FK_AUDIT_RESULTS.md, docs/OMY_CAD_ABLATION_RESULTS.md에 있다. 모든 추적 수치는 첫 프레임 GT 초기화(oracle-first-frame) 조건이고, 9개 validation 시퀀스를 선택과 평가에 함께 썼다. 독립 test와 실사용 초기화 결과는 아직 없다.

구현·실험 안내 빠르게 찾기: 17 · 리뷰 수정 → 18 · 기구학 prior → 19 · 실험 명령 → 20 · 결과 해석. 기존 geometry 규약의 cache는 새로 만들어야 한다. 추적 결과 영상은 21절에서 확인한다.

왜 여러 local token인가? 각 시각 위치가 다른 로봇 영역을 참조할 수 있게 하려는 것이다. 로봇 전체를 하나의 벡터로 줄이면 일반적인 softmax cross-attention의 Key가 하나여서 query에 따른 선택이 사라진다. 다만 cross-attention을 넣었다는 사실만으로 성능이 좋아지는 것은 아니다.

1. 렌더와 관측은 무엇이고, shared CNN → concat → encodeAB는 왜 필요한가?

관측은 카메라가 본 장면이고, 렌더는 현재 pose 후보가 맞다고 가정하고 CAD를 그린 예상 모습이다. 렌더는 GT가 아니다. OMY의 관측은 시뮬레이터에서 생성한 영상이다. 우리 bridge는 두 입력을 각각 RGB+XYZ의 6채널로 구성한다.

CNN은 주변 값에 커널 가중치를 곱하고 더하는 계산 등을 반복해 특징을 만든다. 커널은 사람이 “[-1,0,1]을 써라”라고 지정하는 대신 학습된다. 채널마다 사람이 정한 의미가 있는 것은 아니다.

encodeA는 코드에서 정한 모듈 이름이다. 렌더와 관측에 정확히 같은 CNN 가중치를 적용한다는 뜻이 shared CNN이다. 같은 기준으로 특징을 추출하지만, 이 단계에서는 상대 입력을 직접 보지 않는다.

렌더 → encodeA → 렌더 특징 ─┐
                           ├→ 채널 concat → encodeAB → 결합 특징
관측 → encodeA → 관측 특징 ─┘

Concat은 [렌더 특징 | 관측 특징]을 나란히 붙일 뿐이며 학습 파라미터가 없다. encodeAB는 양쪽과 공간 이웃을 함께 처리해 pose 보정에 유용한 관계를 학습한다. 같은 격자 위치를 붙인다고 같은 물체 표면점끼리 정확히 대응하는 것은 아니다.

두 입력의 encodeA는 같은 가중치를 공유하고, encodeAB는 별도의 가중치를 가진다. 별도 가중치가 있다고 별도로 학습해야 하는 것은 아니다. 원본 refiner는 최종 예측 오차로 앞뒤 층을 함께 학습할 수 있다. 우리 학습에서는 이미 학습된 encodeA와 encodeAB를 고정한다.

2. 특징 지도를 token으로 펼친다는 것은? 위치 정보를 더하면 섞이지 않나?

설명용으로 encodeAB 출력이 20×20 공간 위치, 위치마다 특징 512개라고 하자. 각 위치의 512개 묶음을 유지하며 순서대로 나열하면 400개 token × 512개 숫자가 된다. 모든 숫자를 한 token으로 합치는 것이 아니다. 이 reshape 자체는 새 특징을 학습하지 않는다. 실제 token 수는 crop 크기에 따라 달라진다.

2×2 지도 예시:    A B        목록: [A의 특징, B의 특징, C의 특징, D의 특징]
                 C D        각 위치의 특징 묶음 하나 = token 하나

Token은 데이터 표현 단위이지 transformer 자체가 아니다. CNN의 한 위치는 원본 픽셀 하나가 아니라 주변 영역을 처리한 특징이다.

Self-attention은 목록 순번만 보고 원래 영상의 위치 관계를 자동으로 알지 못한다. 원본 refiner는 펼친 순번으로 만든 고정 sin·cos 위치 벡터를 더한다. 512개 특징에 512개 위치 값을 성분별로 더하므로 길이는 512개 그대로다.

예시 특징: [0.20, 0.80, 0.10, 0.50]
예시 위치: [0.01, 0.02, 0.03, 0.04]  ← 설명용 임의 숫자
합친 입력: [0.21, 0.82, 0.13, 0.54]

두 정보를 완벽하게 분리·복원할 수 있게 보존하는 방식은 아니다. 같은 특징도 위치에 따라 다른 입력이 되게 하고, 뒤의 학습된 계산이 그 차이를 활용하게 한다. 별도의 좌표 칸을 concat하는 것과 다르다. 이 위치는 영상 특징 지도의 위치이며 실제 3D 물체 위치가 아니다.

3. Self-attention과 cross-attention은 무엇인가?

Attention은 참고할 대상의 정보를 입력에 따라 다른 비중으로 섞는 계산이다. Query(Q)는 찾는 기준, Key(K)는 비교할 대상의 특성, Value(V)는 실제 가져올 내용이다. 이들은 문장이 아니라 학습된 Linear 변환으로 만든 벡터다.

Q와 K의 내적 점수 / √(key 차원)
          ↓ softmax: 비중의 합이 1
각 Value의 가중합

예를 들어 [0.1,0.7,0.2]의 비중이면 0.1V₁+0.7V₂+0.2V₃을 가져온다. 비중은 사람이 고정하지 않고 입력마다 계산한다. Attention 가중치는 정확한 물리적 대응이나 인과 설명을 보장하지 않는다.

Self-attention: Q,K,V의 출처가 같은 token 집합이다. Head에서는 시각 token들이 서로 참고한다. Cross-attention: Q와 K,V의 출처가 다르다. 우리 fusion은 시각 token이 Q, 로봇·CAD 기하 token이 K,V다. 결과 개수는 Query token 개수에 맞는다.

CNN도 층을 쌓아 넓은 영역을 처리할 수 있다. Attention의 특징은 멀리 떨어진 token을 직접 참고하고, 참고 비중을 입력에 따라 바꾼다는 점이다. Transformer가 항상 더 좋은 것은 아니며 CNN 등으로 대체하는 설계도 가능하다.

4. Head는 무엇이고, Transformer → Linear → 평균은 왜 하는가?

Head는 특징을 원하는 예측으로 바꾸는 모델 부분의 역할 이름이다. Token이 head로 변하는 것이 아니라 token을 head에 넣는다. 위치와 회전 head는 같은 입력을 받지만 각각 다른 가중치를 가진다.

L개 token × 512개 특징
    ↓ Transformer encoder layer
L개 token × 512개 특징: 다른 위치의 정보도 반영
    ↓ 같은 Linear(512,3)를 각 token에 적용
L개 token × 숫자 3개
    ↓ token 축 평균
출력 숫자 3개

Transformer layer는 self-attention 외에도 잔차 연결, 정규화, feed-forward 계산을 포함한다. 마지막 Linear는 y=W x+b이며 512개 입력의 서로 다른 가중합을 3번 계산한다. 512개 중 3개를 고르는 것이 아니다. 이 Linear만의 파라미터는 3×512+3=1,539개다. MLP는 보통 Linear 사이에 비선형 함수를 둔 구조이며, 여기 마지막 출력층은 Linear 한 층이다.

각 token의 출력은 그 위치의 픽셀을 따로 움직이는 값이 아니다. 물체 전체 보정 출력에 기여하는 값이다. Token마다 정답 보정을 따로 감독하지 않고 최종 집계 결과가 맞도록 학습한다. Head 마지막 평균은 같은 비중의 평균이고, attention 내부의 가중합은 입력에 따라 비중이 달라진다.

회전 head도 숫자 3개를 평균한 후 변환한다. 회전 행렬들을 직접 평균하는 것이 아니다. Attention의 여러 head와 위치·회전 출력 head라는 용어도 구분한다.

5. 평균된 숫자 3개 이후: pose 업데이트와 학습은 어떻게 다른가?

출력은 최종 절대 위치가 아니라 보정용 raw 값이다. XYZ 정규화 설정에서는 위치 출력에 물체 지름의 절반을 곱한다. 지름 0.20m, 출력 [0.2,-0.1,0.3]이면 보정은 [0.02,-0.01,0.03]m다. 정규화를 끈 설정은 tanh와 설정의 translation normalizer를 사용한다.

t_new = t_current + Δt
R_new = ΔR × R_current

현재 위치 [0.10,0.05,0.80]m에 위 보정을 더하면 [0.12,0.04,0.83]m가 된다. 회전 출력은 tanh와 회전 스케일을 거쳐 axis-angle 벡터 r로 해석하고, 표준 회전 행렬 Exp(r)의 transpose를 ΔR로 쓴다(upstream FoundationPose와 같은 규약, 22절). Euler 각 세 개를 그대로 더하는 방식이 아니다. 이 업데이트는 기존 t까지 회전시키는 일반적인 SE(3) 왼쪽 곱과 다르다.

추론: 수정한 pose로 다시 렌더링하고 같은 관측과 비교해 설정 횟수만큼 다듬는다. 가중치는 고정하고 pose를 바꾼다. 학습: 예측 보정의 오차에서 gradient를 구해 학습 대상 가중치를 바꾼다. 보정값 하나를 외우는 것이 아니라 입력에 맞는 보정을 계산하는 함수를 학습한다.

원본 논문 refiner는 위치·회전 업데이트에 대한 supervision을 사용한다. 우리 코드는 보정 pose와 GT pose로 각각 변환한 CAD 표면점 사이의 거리로 loss를 계산하며 선언된 대칭을 고려한다. 위치·회전 head 각각에 별도 정답값 loss를 주는 것과 다르다. 현재 학습은 sample별 한 번의 보정이며 추론 반복을 펼친 sequence 학습이 아니다.

Refiner는 후보를 고치고 scorer는 후보들 중 좋은 것을 고른다. 원본 전체 구조에는 초기 후보 생성과 scorer도 있지만, 우리 변경의 중심은 refiner다.

6. GT pose를 모르는데 CAD 점을 어떻게 쓰는가? Robot state는 무엇을 입력하는가?

알고 있는 CAD 모양과 모르는 현재 pose는 다르다. 컵의 설계도를 알아도 카메라 앞 컵의 위치·방향은 모를 수 있다. CAD 표면점은 물체 자체 좌표계에서 준비할 수 있으므로 현재 GT pose가 필요 없다.

현재·이전 관절 상태 q + 로봇 구조
        ↓ FK: 학습하지 않는 순기구학 계산
같은 로봇 표면점들의 현재·이전 위치
        ↓ 같은 현재 카메라 좌표계에서 차이 / Δt
점의 속도
        ↓ 현재 물체 pose 후보의 좌표계로 변환·크기 정규화
로봇 점 512개 + 물체 CAD 점 256개

CAD 점은 물체 자체 좌표계에 두고 로봇 점을 현재 후보의 좌표계로 표현한다. 후보가 바뀌면 상대적인 로봇 배치가 달라진다. 관절 각도를 바로 MLP에 넣는 구조가 아니다. FK는 정해진 계산이고 이후 point encoder는 학습한다.

점 하나의 11개 값은 위치 3 + 법선 3 + 속도 3 + is_robot 1 + velocity_valid 1이다. 위치·속도는 diameter로 정규화하며 법선은 회전만 적용한다. CAD 속도와 validity는 0이고 geometry 모드는 모든 속도·validity를 0으로 만든다. 접촉 정답이나 GT 현재 pose가 입력에 포함된다는 뜻은 아니다.

7. PointNet++ 계열 encoder는 점들을 어떻게 영역 특징과 token으로 바꾸는가?

점 목록의 이웃은 공간의 이웃이 아니다. 목록을 이미지처럼 취급해 순서대로 공간 CNN을 적용하지 않는다. 우리 encoder는 PointNet++의 계층적 sampling/grouping 원리를 사용한 독립 구현이다.

  1. Sampling: 공간에 분산되도록 대표점을 선택한다. 현재 코드는 farthest-point sampling을 사용한다.
  2. Grouping: 대표점별로 가까운 점을 최대 16개 찾고 반경 밖의 점은 제외한다.
  3. Point별 MLP: 중심에 대한 상대 좌표와 점의 특징을 붙여 같은 MLP에 넣는다.
  4. Max pooling: 이웃 점의 특징을 채널별 최댓값으로 모아 그 영역의 특징 하나를 만든다.
이웃 A 특징: [0.2,0.8,0.1]
이웃 B 특징: [0.7,0.3,0.5]
채널별 max: [0.7,0.8,0.5]

점 하나를 통째로 고르는 것이 아니다. 각 채널의 최대 반응을 모으므로 같은 이웃 집합의 나열 순서에 의존하지 않는다. 어떤 반응이 pose 예측에 유용한지는 학습된다.

768점 × 입력 11개
    ↓ 첫 set abstraction: 정규화 좌표 반경 0.15
128개 대표점 + 영역 특징 64개씩
    ↓ 두 번째 set abstraction: 반경 0.35
32개 대표점 + 영역 특징 128개씩
    ↓ Linear(128,512)
32개 영역 특징 × 512개

첫 단계는 xyz 3개를 이웃 찾기와 상대 좌표 계산에 쓰고, 나머지 8개를 점 특징으로 사용한다. 두 번째는 이전 단계 특징 64개와 상대 좌표를 사용한다. 이웃은 로봇·CAD 혼합 집합에서 찾으며 모든 영역에 반드시 두 종류가 모두 들어가는 것은 아니다.

대표점은 주변 묶음의 기준점이지 평균 좌표나 물체 무게중심이 아니다. PointNet++ 계열 과정의 결과는 대표점 좌표와 영역 특징이다. 그 뒤의 512차원 projection과 위치 MLP 덧셈은 우리 attention 입력 구성이다.

기하 token = Linear(영역 특징 128개) + 위치 MLP(대표점 xyz)
             └── 512개 ──┘           └── 512개 ──┘

좌표 3개를 그대로 512개 특징에 더하지 않는다. 위치 MLP가 3개를 512개로 바꾼다. 이 위치 표현은 학습 가능하며 시각 branch의 고정 sin·cos 패턴과 다르다. 영역 특징도 이미 상대 위치를 이용하므로 위치 정보가 전혀 없었다는 뜻은 아니다.

이렇게 만든 32개 벡터를 token이라고 부른다. Token 하나는 관절 하나나 원본 점 하나가 아니라 주변 공간 영역의 요약이다. 여기서 아직 pose 보정값을 내지는 않는다.

렌더·관측 → 기존 CNN → 시각 token ────────────────┐
                        ↓ Query                 │
로봇·CAD → point encoder → 기하 token → Key/Value │
                                 ↓              │
                          Cross-attention       │
                                 ↓              │
                      α를 곱해 원래 시각 token에 더함

                                 ├→ 위치 head → 위치 보정

정확한 구현은 Q에 visual LayerNorm, K/V에 기하 token LayerNorm을 적용하고, 원래 visual에 attention 출력×α를 더한다. α는 0.01로 시작하는 학습 가능한 스칼라이며 frame별 신뢰 확률이 아니다.

시각 L개와 기하 32개를 단순히 이어 붙여 L+32개로 만드는 것이 아니다. 융합 결과는 시각 token과 같은 L×512 크기다. Cross-attention은 기하 정보를 가져오고, 이후 기존 두 head 내부의 self-attention은 융합된 시각 token들이 서로 참고하게 한다.

우리 변경은 시각 encoder와 pose 보정 형식을 유지하면서 두 부분 사이에 로봇 기하 정보 경로를 추가한 것이다. 이 설계가 실제로 도움을 주는지는 visual·kinematic prior·geometry·motion 비교 실험으로 확인해야 한다.

06 · 정답과 시작 pose는 어떻게 만드는가

학습 샘플은 “물체를 처음 발견하는 문제”보다 주어진 pose를 고치는 문제다. Registration은 별도의 초기화 단계이고, 이 코드의 학습 대상은 refinement다.

모드시작 pose해석
perturbed현재 GT pose에 translation/rotation 노이즈첫 geometry 학습과 구현 검증
previous직전 GT pose를 현재 camera로 옮긴 뒤 노이즈motion과 다음 pose update 관계를 배우는 temporal supervision
평가 rollout직전 모델 prediction오차가 누적되는 실제 tracking 조건

기본 perturbation은 translation 각 축 표준편차 0.01m, rotation axis-angle 각 성분 표준편차 10°다. “언제나 정확히 10mm·10° 틀린다”는 뜻이 아니다. 표준편차가 있는 확률 분포에서 뽑는다.

Previous 모드는 선택 프레임이 5프레임 간격이어도 실제 직전 프레임 i−1의 pose를 사용한다. frame 0에는 이전 object GT가 없으므로 제외한다. 이를 문서에서 teacher-forced hypothesis라고 부른다. 이전 GT를 쓰지만 recurrent sequence 모델을 학습하는 것은 아니며, 현재는 각 sample을 독립적인 한 번의 refinement로 학습한다. 모델 자신의 이전 prediction 분포를 쓰는 on-policy 학습도 아니다.

GT를 학습 target이나 학습용 hypothesis 생성에 쓰는 것은 supervised learning의 일부다. 추론에서 매 프레임 GT를 넣거나, validation 정답으로 tracking을 계속 초기화하면 다른 평가가 된다.

07 · 왜 먼저 cache를 만드는가

Rendering과 visual encoder는 GPU 비용이 들지만, 이번에는 visual encoder를 고정한다. 같은 sample을 20번 학습하면서 같은 렌더링을 20번 할 필요가 없으므로 visual token을 한 번 저장한다.

prepare_robot_refiner.py
  sequence 읽기 → hypothesis 만들기
  → RenderBridge.pair(): 실제 RGB-D와 렌더 crop 구성
  → model.encode_visual(): frozen feature 추출
  → point features + target + CAD와 함께 sample .pt 저장
  → heads.pt, manifest.json 저장

train_robot_refiner.py
  cache 읽기 → robot encoder → fusion → pose heads
  → loss → backward → optimizer.step()

Cache에는 visual, points, hypothesis, target, CAD, diameter, symmetries가 들어 있다. Manifest는 weight hash, upstream commit, config, sequence hash와 parent group을 기록한다. 서로 다른 원본 weights나 config의 cache를 섞으면 거부한다.

Hypothesis를 바꾸면 렌더 crop과 visual token도 바뀐다. 그래서 temporal cache는 별도로 만든다. 이 방식은 fixed augmentation이다. 더 많은 epoch를 돌려도 새로운 random perturbation이 자동으로 생성되지는 않는다.

08 · 학습 step 안에서는 무슨 일이 일어나는가

for batch in train_loader:
    optimizer.zero_grad(set_to_none=True)
    output = model.forward_tokens(batch['visual'], batch['points'])
    predicted_pose = decode_pose(output, batch['hypothesis'], ...)
    loss = pose_loss(predicted_pose, batch['target'], batch['cad'], ...)
    loss.backward()
    clip_grad_norm_(model.parameters(), 1.0)
    optimizer.step()

이 코드는 개념을 보여주기 위해 인자를 줄인 것이다. 실제 구현은 trainer.py의 batch_loss()와 run()에 있다. AdamW는 gradient의 누적 통계도 가지고 있어서 resume에 optimizer state가 필요하다. Gradient clipping은 전체 gradient norm이 1을 넘으면 크기를 제한한다. 현재 warmup은 heads freeze 기간이며 learning-rate ramp가 아니다.

각 epoch가 끝나면 model.eval()과 no_grad()로 validation을 수행한다. Validation에서는 weight를 업데이트하지 않는다. 이 결과가 가장 낮으면 best.pt를 갱신하고, 마지막 상태는 last.pt에 저장한다.

Frozen heads인데 어떻게 encoder가 학습되는가?

heads weight의 requires_grad=False는 weight를 바꾸지 않겠다는 뜻이다. heads가 입력 특징에 수행하는 연산은 여전히 미분 가능하다. loss의 gradient는 heads를 통과해 fusion과 robot encoder로 전달된다. 따라서 heads 전체를 no_grad로 감싸면 이 학습 경로를 끊을 수 있다. 현재 visual encoder와 그 앞단은 학습 대상이 아니므로 cache 생성에서 no_grad를 사용한다. 반면 Tiny heads는 weight가 고정돼도 train 모드의 dropout은 켜져 있다. 23절에서 freeze/no_grad/eval을 구분한다.

09 · Loss와 hyperparameter를 읽는 법

예측 pose로 변환한 CAD점과 GT pose로 변환한 같은 CAD점 사이의 거리를 평균한다.

L = meanᵢ ‖ T̂ pᵢ − Tᴳᵀ pᵢ ‖₂

정확한 대칭 변환이 제공되면 허용된 변환 중 최소 오차를 택한다. 없으면 identity만 사용한다. 원통처럼 보인다는 이유로 texture·형상의 대칭을 임의로 선언하지 않는다. 이 loss는 무조건 최근접점을 찾는 ADD-S와 같은 정의가 아니다.

예를 들어 surface error 0.004는 평균 4mm다. 이것은 translation error 4mm와 같지 않다. 회전이 틀려도 표면점 위치가 어긋나기 때문이다.

13 · 학습 완료 후 무엇을 증명해야 하는가

먼저 pretrained visual control, same-data visual-only, geometry, geometry+motion을 같은 초기화·mask·split 조건에서 비교한다. Geometry와 motion 비교는 같은 temporal cache에서 해야 hypothesis 차이를 robot motion 효과로 혼동하지 않는다.

  • A/B/C, 가시성 구간별 error와 실패율을 따로 본다.
  • 정확한 state와 시간 지연/교란 state를 비교해 robot 정보를 실제로 쓰는지 본다.
  • 새 branch에는 CAD점도 추가되므로 robot 정보만의 효과를 더 분리하려면 object-CAD-only 대조군을 추가한다.
  • 안정적인 grasp의 gripper-motion propagation과 그 prior를 사용하는 pretrained refinement를 18~19절에서 실제 비교한다.
  • C의 부분 가림 초기화는 별도 병목이다. 동일 GT 초기화 진단과 실제 initialization 평가를 구분한다.

현재 evaluate_robot_tracker는 동일 RenderBridge의 sequence runner다. upstream track_one의 모든 전처리와 완전 동일하다는 보장은 아니다. 자체 초기화·실패 감지·재초기화 모듈도 아직 없다.

우리의 contribution 후보는 “encoder 두 개를 합쳤다”가 아니라, 조작 중 robot geometry·motion이 visual tracking을 보완하는 조건을 분리해 보이는 것이다. 기존 V-HOP 등 관련 연구가 있으므로 구조 자체의 최초성이나 효과를 아직 주장하지 않는다.

NaN / non-finite lossdepth 단위, transform, diameter, sample 대응, learning rate 확인. 오류를 무시하고 더 돌리지 않기.
Resume provenance mismatch같은 cache·mode·weights/config인지 확인. cache를 바꾼 재개는 지원하지 않음.

처음은 단일 GPU FP32로 진행한다. AMP/BF16, 다중 GPU, 추가 custom CUDA 최적화는 correctness가 확인된 뒤 검토한다. 특히 renderer와 pose geometry를 무조건 낮은 정밀도로 바꾸지 않는다.

15 · 이해했는지 스스로 확인하기

Q1. Tiny에서 pose heads를 고정하면 gradient도 끊길까?

아니다. weight 업데이트만 막는다. heads 연산을 통해 입력 특징으로 gradient가 전달된다.

Q2. 20 epochs면 새로운 hypothesis를 20번 만들까?

아니다. 현재 fixed cache는 같은 hypothesis를 재사용한다. 새 perturbation에는 새 cache가 필요하다.

Q3. Robot 속도만 추가하면 temporal training인가?

속도는 두 시점의 정보이지만 현재 신경망에 sequence memory가 생기는 것은 아니다. Previous hypothesis는 이전 pose를 현재 pose로 고치는 supervision을 만들며 각 sample은 독립적으로 학습된다.

Q4. Train loss 0.003이면 translation 오차 3mm인가?

그렇지 않다. CAD surface 평균 거리 3mm이며 위치와 회전 오차가 함께 반영된다.

Q5. 9개 validation에서 가장 좋은 모델이면 최종 test 성능인가?

아니다. 그 데이터로 모델을 선택했으므로 독립 test가 아니다.

Q6. 5080에서 Isaac Sim이 실행되면 학습 환경도 준비된 걸까?

아니다. FoundationPose의 PyTorch·CUDA·native extension·weights와 실제 rendering gate를 확인해야 한다.

17 · 코드 리뷰에서 수정한 문제

1. 이번 수정이 해결하는 문제

가중치 경로: 서로 다른 컴퓨터의 ckpt_dir 절대 경로는 동일성 비교에서 제외한다. 대신 가중치 파일의 SHA-256과 나머지 config를 엄격히 비교한다. 다른 가중치를 같은 이름으로 바꿔도 통과하지 않는다. train/validation cache 비교, resume, CUDA 검사, rollout 모두 같은 규칙을 사용한다.

물체 diameter: 이전에는 mesh vertex를 무작위로 뽑아 계산해 crop·translation decoding의 스케일이 달라질 수 있었다. 이제 convex hull의 vertex 간 최대 거리를 정확히 계산한다. 퇴화한 평면/선 mesh는 전체 vertex를 사용하며 메모리는 작은 block으로 제한한다. 학습 cache와 rollout은 exact-vertex-diameter-v1을 공유한다. cache format 3에는 mesh geometry hash와 실제 diameter도 기록한다. 매우 복잡한 hull은 준비 시간이 길 수 있지만 프레임마다 계산하지 않는다.

반복 I/O/FK: OMY adapter는 manifest, 관측 JSONL, preroll, joint inventory를 한 번만 읽는다. 최근 FK 3개, 현재 frame의 robot surface, RGB-D 1개를 보관한다. 같은 프레임의 refinement에서는 hypothesis 좌표 변환만 다시 한다. 이전 surface는 이전 시점의 robot base pose도 반영한다. 공개 dataset reader 원본은 유지하며 학습 adapter가 이 경로를 직접 구현한다.

평가: 학습용 256점과 다른 seed로 면적 비례 CAD 4,096점을 뽑는다. 전체 예측을 끝낸 뒤 GT로 채점하고, 초기화 프레임을 평균에서 뺀다. 실제 rollout, 마지막 프레임 drift, 임계 초과 비율을 기록한다. best.pt는 여전히 one-step validation loss 기준이며 tracking 성능이 가장 좋은 모델이라는 뜻은 아니다.

이전 cache와 checkpoint는 새 geometry 규약에서 거부한다. 기존 파일을 수정하거나 지우지 말고 새 OMY_WORK에서 cache 생성부터 다시 시작한다. checkpoint의 version 문자열만 고쳐 통과시키면 안 된다.

18 · 기구학 prior를 식과 비교군으로 이해하기

2. 기구학 prior가 하는 일

T_AB는 B 좌표를 A 좌표로 변환한다. W는 world, C는 camera, E는 link6의 rigid frame, M은 raw object mesh다. 입력은 이전 추정 pose와 현재/이전 측정 관절값으로 계산한 FK다.

T_WM(previous) = T_WC(previous) · estimated_T_CM(previous)
Delta_T_world = T_WE(current) · inverse(T_WE(previous))
prior_T_CM(current) = inverse(T_WC(current)) · Delta_T_world · T_WM(previous)

그리퍼와 물체가 고정된 관계를 유지하면 이 식으로 물체의 위치와 회전을 함께 예측할 수 있다. 회전 시 물체 중심이 손목을 중심으로 움직이는 lever arm도 포함한다. 단순히 gripper 이동량을 xyz에 더하는 구현과 다르다. 카메라가 움직이는 경우도 보상한다.

현재 프로젝트의 tool carrier는 link6다. 고정 tool offset을 양쪽 시점에 동일하게 적용하면 T_WE(t) · inverse(T_WE(t-1))에서 상쇄되므로 baseline에는 별도의 tool offset을 추정할 필요가 없다. 손가락처럼 gripper 개폐로 별도 운동하는 link를 선택하면 rigid-grasp 가정과 맞지 않는다. 다른 robot에서는 --effector-link를 명시한다. 잘못된 link 이름은 실행 초기에 거부한다.

이 prior는 항상 rigid grasp를 가정한다. A 비접촉 가림, B의 grasp 전 구간, C의 release 후 구간에서도 로봇을 따라가므로 틀릴 수 있다. GT contact/phase로 적절한 구간만 골라 prior를 적용하지 않는다. 이는 baseline의 알려진 가정이며, 바로 그 실패가 학습 모델이 해결해야 할 비교 대상이다. 마찰·slip·외력은 모델링하지 않는다.

3. 비교할 방법

hold: 물체가 world에 고정돼 있다고 가정하고 camera motion만 보상한다. RGB-D나 신경망을 사용하지 않는 CPU control이다. A/C에서 물체가 정지해 있는 비중이 높아 평균이 좋게 보이는지 확인한다.

kinematic: 매 프레임 위 식으로만 propagate한다. CPU에서 실행하며 학습·FoundationPose weights·CUDA가 필요 없다. 단, torch/numpy/scipy/trimesh/Pillow 등 reader 의존성은 필요하다.

visual: 직전 추정 pose에 camera motion만 보상한 뒤 pretrained FoundationPose refiner를 적용한다. robot input은 사용하지 않는다.

kinematic-refine: 기구학 prior를 한 프레임당 한 번 적용한 뒤 동일 pretrained refiner로 보정한다. refinement를 2번 해도 prior를 2번 적용하지 않는다. 새 학습 파라미터가 없다. 신경망 fusion이 넘어야 할 가장 중요한 단순 비교 대상이다.

learned: 학습된 checkpoint의 visual / geometry / motion 모드로 추적한다. 기구학 prior는 자동으로 추가하지 않는다. 모델 자체가 robot 정보를 어떻게 쓰는지 평가하기 위해서다. 두 기법을 결합하는 실험은 이번 구현의 범위 밖이다.

모든 방법은 같은 frame-0 T_camera_raw_mesh를 그대로 출력하고 frame 1부터 추적한다. frame 0에 어떤 방법만 추가 refinement를 해 유리한 출발점을 만들지 않는다. 중간 GT reset, oracle mask, 실패 후 자동 재초기화는 없다. 기존 evaluator의 frame-0 refinement 결과와 새 protocol 2 결과를 직접 섞지 않는다.

8. 결과 파일과 읽는 순서

comparison.md: 전체 방법의 all/A/B/C 비교표. error는 mm, threshold 초과율은 %, 프레임 처리 시간은 ms로 표시한다. all은 시퀀스별 평균을 같은 비중으로 평균한다. 긴 clip의 프레임 수로 가중하지 않는다.

comparison.json: 같은 요약의 원시 수치. 거리 단위는 m, 시간은 s, 실패 비율은 0~1이다. A/B/C는 시퀀스 이름의 clip 분류이며 frame별 contact/phase나 visibility bucket을 뜻하지 않는다. B/C가 같은 physical parent일 수 있으므로 9개 모두가 통계적으로 독립이라고 간주하지 않는다.

<label>/<sequence>/run.json: 초기 pose hash와 초기화 종류, checkpoint hash, pretrained hash, mesh hash/diameter 규약, 입력 manifest/관측 hash, source commit, iteration, 평가점 수를 기록한다. poses.jsonl은 추론값만, frame_metrics.jsonl은 예측 완료 후 계산한 GT 오차만 담는다. summary.json은 초기 오차, 평균·중앙값·95백분위·마지막 오차, diameter 10% 초과 비율을 담는다.

오차는 선언된 symmetry 변환 중 가장 작은 corresponding surface distance다. identity만 선언돼 있으면 일반 corresponding-point error다. 최근접점을 찾는 ADD-S도, 표준 BOP AR도 아니다. failure_fraction_10pct_diameter는 편의를 위한 프레임 오차 임계 초과율이며 물리적 grasp 실패율이나 자동 tracker failure detector가 아니다.

시간은 frame I/O, FK, crop/render, inference와 GPU 동기화를 포함하며 setup, scoring, 파일 쓰기는 제외한다. 첫 추적 프레임의 warm-up과 OS cache 영향이 있으므로 정밀 GPU kernel benchmark나 보장 FPS로 해석하지 않는다. CPU baseline은 영상 읽기가 없으므로 처리량을 신경망과 같은 연산량으로 비교하지 않는다.

실행 중 실패하면 traceback을 확인하고, 완료되지 않은 작업만 출력된 개별 evaluate 명령으로 새 디렉터리에 실행한다. 이미 완료한 파일을 삭제하지 않는다. suite output에서 아직 생성되지 않은 sequence 경로를 그대로 채운 경우에는 같은 suite 명령에 --execute 대신 --summarize-only를 붙여 표를 만든다. 서로 다른 초기 pose/geometry/evaluation 규약이나 source commit이 섞이면 합산을 거부한다. 같은 label 안의 checkpoint 설정 및 visual 방법 사이의 pretrained weights/config/refinement 횟수도 검사한다.

20 · 결과로 연구 방향을 판단하기

9. 어떤 결과가 연구 방향을 바꾸는가

kinematic-refine만으로 motion 모델과 비슷하거나 더 좋다면, 우선 단순 baseline을 채택하고 큰 fusion 모델의 필요성을 재검토한다. 추가 신경망이 의미 있으려면 비접촉 가림, slip, release 등 rigid prior가 틀리는 조건에서 더 안정적이라는 근거가 필요하다.

kinematic이 B에서 좋고 A/C에서 나쁘다면, 다음 연구 질문은 “robot 정보를 더 많이 넣을까”보다 언제 robot motion을 신뢰할까가 된다. 향후 vision과 proprioception만으로 trust weight를 추정하거나, visual/kinematic 후보 중 residual을 예측하는 작은 모델을 고려할 수 있다. GT contact/phase로 gate를 켠 성능은 별도의 oracle upper-bound 실험으로만 취급한다. 이 gate는 아직 구현되지 않았다.

geometry가 visual-ft보다 좋지만 motion은 더 좋지 않다면, geometry의 가림 해석 이득과 실제 동작 정보의 이득을 분리한다. object-CAD-only, robot state 시간 지연/교란, visibility별 분석은 이후 추가 실험이며 이번 자동 비교에 포함되지 않는다.

좋은 one-step loss에도 rollout이 나쁘면, 더 긴 학습보다 실제 tracker prediction 근방의 hypothesis로 cache를 확장하는 것이 우선 후보다. 아직 fixed teacher-forced cache이며 temporal memory나 sequence loss를 학습한 모델이 아니다.

프로젝트의 의미는 “encoder+fusion을 붙였다”만으로 성립하지 않는다. 가림·접촉 전후에서 단순 기구학보다 나은 관측 가능한 신뢰 판단을 보여주고, held-out parent·새 물체·실측 데이터로 일반화까지 확인할 때 더 강해진다. 현재 45개 시퀀스는 이 가설을 판별하는 pilot이고 일반적인 novel-object tracking의 증거는 아니다.

10. Compute와 검증 범위

hold/kinematic은 CPU로 실행할 수 있다. visual/kinematic-refine 및 learned rollout은 FoundationPose renderer 때문에 CUDA GPU가 필요하다. 학습 준비 때 확인한 5080 한 대에서 순차 실행하도록 구성했으며 AWS 연결이나 인스턴스는 생성하지 않는다. 정확한 VRAM과 시간은 실측 전이다. batch 4 FP32부터 기존 smoke/tiny gate로 확인한다.

baseline suite는 9개 × 4개 방법이며, learned checkpoint를 하나 추가할 때 9개 rollout이 추가된다. temporal 기본 비교는 7개 방법 × 9개 = 63개 sequence rollout이다. validation 2,382프레임에서 초기화 9개를 제외한 2,373개 frame을 방법별로 추적한다. visual 계열의 기본 iteration은 2이므로 순차 평가 시간이 학습 시간보다 길 수 있다. 먼저 한 B clip으로 실제 시간을 측정한다.

CPU 합성 테스트는 좌표계·입력 누출 방지·파일 출력·집계·경로 이동·diameter 재현성의 논리를 확인한다. 실제 CAD/관절 보정의 정확성, raw dataset checksum, CUDA rendering, 실제 학습 수렴, 5080 VRAM 및 성능 개선은 GPU 머신에서 확인해야 한다. 성공 수치는 실행 후 생성되는 결과만 보고한다.

영상으로 추적을 검사하려면 OMY_TRACKING_VISUALIZATION.md 또는 단일 HTML 21절을 따른다. 저장된 poses.jsonl에서 RGB / 추정+GT / robot FK / 전체 겹침 MP4와 PNG를 생성한다.

21 · 추적 결과를 영상으로 확인하기

visualize_robot_tracker.py는 저장된 추정 pose를 RGB에 투영하고, 물체 GT와 측정 관절값 기반 로봇 FK를 겹쳐 보여주는 추론 후 진단 도구다. 기존 추적 결과를 다시 학습하거나 수정하지 않는다. CPU에서 실행하며 FoundationPose weights와 CUDA renderer가 필요 없다. 현재 OMY packaged sequence를 지원한다.

1. 화면과 색상 읽기

기본 출력은 네 칸이다. 좌측 위는 원본 RGB, 우측 위는 추정 pose + GT, 좌측 아래는 로봇 FK, 우측 아래는 세 가지를 모두 겹친 화면이다. 각 화면에서 같은 프레임을 동시에 비교할 수 있다.

청록색 P: 저장된 추정 T_camera_raw_mesh에 물체 CAD를 놓는다. 물체의 mesh edge 일부와 실선 bounding box, P:X/Y/Z 축을 표시한다. bounding box는 raw mesh 좌표계에서 만든 3D box이며 매 프레임 영상에서 다시 맞춘 2D box가 아니다.

분홍색 G: GT pose에 같은 CAD를 놓고 점선 box와 G:X/Y/Z 축을 표시한다. GT는 inverse(T_world_camera) · T_world_object_gt · T_object_mesh로 raw mesh 좌표에 맞춘다. 정확히 겹치면 일부 선이 가려질 수 있으므로 점선 box와 별도 RGB 화면을 함께 본다.

노란색 E / 로봇 선: 로봇 link mesh를 현재 measured joint positions와 joint inventory의 FK로 변환한다. E:X/Y/Z는 기본값 link6의 좌표축이다. simulator의 정답 link transform은 사용하지 않는다. 로봇의 전체 geometry link는 함께 표시한다.

상단에는 frame ID, 첫 프레임 대비 시간, 색상 범례가 나온다. run.json이 함께 있으면 방법명·학습 모드·oracle-first-frame 또는 external 초기화 종류도 표시한다. frame 0은 INITIAL POSE로 표시한다. 출처 정보가 없는 수입 pose 파일은 초기화 종류를 확인하지 못했다는 문구가 나온다.

이 영상은 X-ray 진단 표시다. 카메라 뒤쪽과 화면 밖의 선은 잘라내지만, 물체나 로봇에 가려진 표면은 숨기지 않는다. 노란 선이 물체를 관통해 보인다고 곧바로 충돌이나 FK 오류로 판단하면 안 된다. 일부 edge만 고정 선택해 그리므로 완전한 mesh silhouette나 pixel mask가 아니다. 시각화는 자동 정확도 평가를 대체하지 않는다.

2. 코드와 영상 저장 의존성 준비

기존 clone에서 변경사항을 저장한 뒤 같은 브랜치의 최신 코드를 받는다. Python은 기존 학습 환경을 사용한다. CPU 전용 환경이라면 torch와 requirements-training.txt의 reader 의존성을 먼저 준비한다. 이 추가 requirements는 torch/CUDA를 교체하지 않는다.

git switch feat/omy-training-ready
git pull --ff-only origin feat/omy-training-ready
python -m pip install -r requirements-visualization.txt

추가 패키지 imageio-ffmpeg는 CPU MP4 저장용이다. FFmpeg를 사용할 수 없거나 설치하고 싶지 않으면 아래 명령에 --png-only를 붙이면 된다. 이 경우 선택한 모든 프레임을 PNG로 저장하고 MP4는 만들지 않는다.

3. 한 시퀀스의 추적 결과 시각화

앞선 비교 실험에서 만든 poses.jsonl을 입력으로 사용한다. 아래 예시는 HTML 19절의 pilot 비교가 끝난 상태에서 box_B_04 geometry 모델 결과를 시각화한다. OMY_DATASET, OMY_EVAL은 해당 실험의 실제 경로여야 한다.

python scripts/visualize_robot_tracker.py "$OMY_DATASET/box_B_04" \
  --poses "$OMY_EVAL/pilot/geometry/box_B_04/poses.jsonl" \
  --output "$OMY_EVAL/videos/geometry-box-B"

학습 없이 만든 baseline 결과를 먼저 보려면 다음을 실행한다.

python scripts/visualize_robot_tracker.py "$OMY_DATASET/box_B_04" \
  --poses "$OMY_EVAL/pretrained-baselines/kinematic-refine/box_B_04/poses.jsonl" \
  --output "$OMY_EVAL/videos/kinematic-refine-box-B"

--poses는 checkpoint 파일이 아니라 추적이 이미 끝난 pose 기록이다. 아직 추적하지 않았다면 19절의 evaluate_robot_tracker.py 또는 run_omy_comparison.py를 먼저 실행한다. 예측이 올바른지 검사하기 위한 영상이지 새 prediction을 생성하는 명령이 아니다.

4. 출력 파일 열기

overlay.mp4를 일반 동영상 플레이어에서 연다. 기본은 패널당 최대 640px인 네 칸 영상이며 원본보다 확대하지 않는다. preview.png는 선택한 첫 프레임의 동일한 그림이다.

frames.jsonl에는 출력 영상의 프레임 순서와 원본 frame_index/frame_id, 관측 timestamp, 영상 시간이 대응돼 있다. 그려진 box/robot edge 수가 0이면 화면 밖 또는 카메라 뒤쪽에 pose가 있는지 확인한다. 이 수치는 visibility fraction이나 정확도 점수가 아니다.

visualization.json에는 입력 pose·관측·joint inventory·GT·mesh hash, 사용한 구간/stride, 영상 크기/FPS와 출처 확인 결과를 기록한다. 같은 폴더의 run.json이 있으면 sequence와 기록된 입력 hash, object mesh가 맞는지 먼저 확인한다. 다르면 섞인 결과를 그리는 대신 중단한다. run.json이 없으면 frame 순서·수·pose 형식은 검사하되 provenance는 unverified로 기록한다. pose가 좋은지 나쁜지의 판정과는 다르다.

출력은 새 디렉터리에만 생성한다. 기존 결과와 raw dataset 안에는 덮어쓰지 않는다. RGB 원본, GT, 예측 pose와 모델 가중치는 변경하지 않는다.

5. 짧은 구간·한 화면·정지 이미지

먼저 30~89번 프레임을 2프레임 간격으로 확인하는 예시다. --start는 포함하고 --stop은 포함하지 않는다. frame ID가 아니라 관측 배열의 0부터 시작하는 index다. --stride 2는 30Hz 원본에서 15FPS로 저장하므로 움직임을 두 배 빠르게 재생하지 않는다.

python scripts/visualize_robot_tracker.py "$OMY_DATASET/box_B_04" \
  --poses "$OMY_EVAL/pilot/geometry/box_B_04/poses.jsonl" \
  --output "$OMY_EVAL/videos/geometry-box-B-detail" \
  --start 30 --stop 90 --stride 2 --save-frames

--save-frames는 MP4와 함께 frames/000030.png처럼 원본 index 이름의 정지 이미지를 저장한다. 번호가 건너뛰는 것은 stride 때문이다. 짧은 구간을 고를 때는 영상의 t=0이 원본 clip의 t=0과 다를 수 있으므로 화면의 시간과 mapping 파일을 함께 확인한다.

보고서용으로 전체 겹침 한 화면만 만들거나 더 크게 보고 싶을 때는 다음 옵션을 사용한다.

python scripts/visualize_robot_tracker.py "$OMY_DATASET/box_B_04" \
  --poses "$OMY_EVAL/pilot/geometry/box_B_04/poses.jsonl" \
  --output "$OMY_EVAL/videos/geometry-box-B-overlay" \
  --layout overlay --panel-width 960

카메라 내참수 K도 RGB의 축소 비율과 pixel-center 위치에 맞춰 함께 변환한다. H.264 영상 크기는 필요한 경우 가장자리에 1px을 덧붙여 짝수로 만들며, 16배수 크기를 맞추기 위해 영상을 임의로 늘리지 않는다.

느리거나 선이 너무 복잡하면 --object-edges 256 --robot-edges-per-link 64로 줄일 수 있다. 기본은 물체 512개 edge, 로봇 link당 128개 edge다. edge 샘플은 프레임마다 바뀌지 않는다. mesh edge를 줄여도 box와 좌표축은 유지한다.

6. GT가 없거나 추적이 중간에 멈췄을 때

실제 관측처럼 GT가 없으면 --no-gt를 명시한다. GT pose와 GT hash를 읽지 않고 추정 pose와 robot FK만 그린다. run.json의 GT hash 확인도 생략하며 출처 기록에 표시한다. 잘못된 GT 파일을 조용히 숨기는 기본 동작은 없다.

추적 중 오류로 poses.jsonl이 앞부분만 저장됐으면 --allow-partial을 추가한다. frame 0부터 연속으로 정렬된 prefix만 허용한다. 중간 frame 누락, 순서 뒤바뀜, 잘못된 frame ID는 이 옵션으로 무시하지 않는다. partial 결과임을 metadata에 기록하며 전체 성능 평가로 취급하지 않는다.

python scripts/visualize_robot_tracker.py "$OMY_DATASET/box_B_04" \
  --poses "$OMY_EVAL/interrupted-run/poses.jsonl" \
  --output "$OMY_EVAL/videos/interrupted-debug" \
  --allow-partial --png-only

7. 무엇을 먼저 볼까

A에서는 물체가 정지해 있는데 추정 pose만 로봇을 따라 움직이는지 본다. B에서는 grasp 이후 물체 회전과 이동을 함께 따라가는지, 가림 중 drift가 커지는지 확인한다. C에서는 release 후에도 물체를 로봇에 붙어 있는 것으로 추정하는지 본다. 이 분류는 화면 해석 가이드이며 모델 입력에 접촉 정답을 넣는다는 뜻이 아니다.

로봇 FK가 RGB의 로봇과 계속 어긋나면 먼저 camera/base calibration, joint 순서와 단위, timestamp를 점검한다. 추정과 GT가 모두 물체에서 같은 방향으로 어긋나면 raw mesh/object-root/centered mesh 변환과 K를 점검한다. GT만 잘 맞고 추정이 시간이 지날수록 어긋나면 tracking drift 가능성을 본다. 정확한 원인 판정에는 pose 기록과 수치 평가도 함께 필요하다.

현재 검증은 합성 scene에서 투영·near-plane clipping·움직이는 FK·GT mesh offset·프레임 정렬·PNG 저장·실제 MP4 encode/decode를 확인한 것이다. 실제 OMY RGB와의 정합이나 학습 성능은 GPU 머신에서 만든 추적 결과로 확인해야 한다. 이번 시각화 추가 때문에 학습 cache를 다시 만들 필요는 없다. 앞서 diameter 규약이 바뀌기 전의 cache를 새로 만들어야 한다는 규칙은 그대로다.

22 · 좌표계와 pose: 필요한 수학부터

Pose는 “물체가 어디 있고 어느 방향을 향하는가”다. 위치와 방향을 수치로 바꿔야 영상, 로봇, CAD를 같은 공간에서 비교할 수 있다.

벡터·행렬·tensor부터

벡터 p = [x, y, z]는 3차원 점 하나다. 3×3 회전행렬 R은 그 점의 방향을 돌리는 연산이고, 3차원 t를 더하면 위치를 옮긴다. Tensor는 여러 축을 가진 숫자 배열이다. 예를 들어 [4, 768, 11]은 “sample 4개 × 점 768개 × 점마다 숫자 11개”다. 이 모양을 shape라고 하며, 11이 11차원 공간의 위치라는 뜻은 아니다.

물체 pose의 자유도는 위치 3개와 회전 3개로 총 6개다. 회전행렬에는 숫자가 9개 있지만 각 열이 서로 수직인 단위벡터라는 제약 때문에 독립적인 자유도는 3개다. 유효한 회전은 RᵀR = I, det(R) = +1을 만족한다.

같은 점도 좌표계에 따라 숫자가 달라진다

p_camera = R_camera_mesh · p_mesh + t_camera_mesh

              ┌ R00 R01 R02 tx ┐
T_camera_mesh =│ R10 R11 R12 ty │
              │ R20 R21 R22 tz │
              └  0   0   0  1 ┘

[p_camera, 1]ᵀ = T_camera_mesh · [p_mesh, 1]ᵀ

아래 첨자는 오른쪽에서 왼쪽으로 읽는다. T_camera_mesh는 mesh 좌표를 camera 좌표로 바꾼다. 단위는 m다. 회전이 없고 물체 원점이 카메라 앞 1m에 있다면 mesh의 점 (0.02, 0, 0)은 카메라에서 (0.02, 0, 1)이 된다. 이때 translation의 크기 1m는 “카메라에서 물체 원점까지의 위치”이고, 물체 크기 2cm와 다른 값이다.

T_camera_object · T_object_mesh처럼 중간 좌표 이름이 맞으면 연결할 수 있다. 역행렬은 반대 방향 변환이다. 곱셈 순서를 바꾸면 보통 다른 결과가 나온다. 행렬 합성의 기본은 Modern Robotics 3.3.1의 설명과 연결해 읽자. 우리 코드는 점을 N×3 행 배열로 저장해서 points @ R.T + t로 계산하지만, 수학적 좌표 규약은 같은 column-vector 규약이다.

3D 점이 영상 pixel이 되는 과정

u = fx · X/Z + cx
v = fy · Y/Z + cy

예시: fx=fy=600 px, (cx,cy)=(320,240) px
카메라 점 (X,Y,Z)=(0.02,0,1) m → pixel (u,v)=(332,240)

fx, fy는 pixel 단위 초점거리이고 cx, cy는 주점이다. 이 네 값이 K라는 내참수 행렬에 들어간다. 같은 2cm라도 가까운 물체에서는 더 많은 pixel을 움직인다. OpenCV camera의 +X는 오른쪽, +Y는 아래쪽, +Z는 카메라 앞이다. Z≤0인 점을 정상 영상 좌표처럼 나누면 안 된다. 우리 시각화 도구는 화면과 near-plane에서 선을 잘라낸다.

RGB-D의 D는 이 데이터에서 optical-axis 깊이 Z다. PNG의 1000은 1000m가 아니라 1000mm = 1m다. X=(u−cx)Z/fx, Y=(v−cy)Z/fy로 depth를 XYZ map으로 바꿀 수 있다. 신경망의 visual 입력은 단순 RGB 3채널만이 아니라 렌더/관측 각각의 RGB+XYZ crop이다. 0 depth는 유효한 표면 깊이가 아니다.

왜 diameter로 나눌까

2cm라는 거리도 작은 물체와 큰 물체에서는 의미가 다르다. 직경 d=0.1m일 때 상대 위치 0.02m를 d로 나누면 0.2라는 무차원 비율이 된다. 속도 0.1m/s를 d로 나누면 1/s다. 법선은 표면의 방향을 나타내는 단위벡터라 translation을 더하지 않고 회전만 적용한다. 속도 벡터도 점의 위치가 아니므로 좌표계 변환에서 translation을 더하지 않는다. 이 정규화가 모든 물체 크기에 대한 일반화를 자동 보장하는 것은 아니다.

회전 출력 세 숫자를 어떻게 이해할까

현재 decoder는 axis-angle 벡터를 쓴다. 벡터의 방향은 회전축, 길이는 회전각(rad)이다. [0, 0, π/2]는 Z축 90° 회전이다. Euler의 roll/pitch/yaw 세 숫자와 같은 표현이 아니다. 또한 6D pose와 일부 논문에서 말하는 6D rotation representation은 다른 용어다. 현재 코드의 rotation 출력은 3개다.

현재 geometry.decode_pose의 규칙:
r = tanh(rotation_head_output) · rot_normalizer
ΔR = Exp(r)ᵀ      # 표준 axis-angle 회전행렬의 transpose
R_new = ΔR · R_hypothesis

normalize_xyz=True : Δt = translation_head_output · diameter/2
normalize_xyz=False: Δt = tanh(translation_head_output) · trans_normalizer
t_new = t_hypothesis + Δt

ΔR에 transpose가 붙는 이유: upstream FoundationPose는 so3_exp_map(r).permute(0, 2, 1)를 쓴다. pytorch3d의 so3_exp_map은 표준 Rodrigues 회전 Exp(r)이므로 upstream의 ΔR은 그 transpose, 즉 같은 축으로 반대 방향 회전이다. 초기 코드는 Exp(r)을 그대로 써서 pretrained head와 반대로 회전했다. 2026-11-26 GPU parity 검사에서 발견해 고쳤고(geometry.decode_pose), scipy 기준 회귀 테스트가 있다. 수정 전에 만든 cache·checkpoint는 재사용하지 않는다.

Head의 raw output은 바로 m나 degree가 아니다. 저장된 upstream config를 통해 해석해야 한다. 이 decoder는 rotation과 translation을 분리해 업데이트하므로 무조건 T_new = ΔT · T_old로 대체하면 안 된다. 일반적인 왼쪽 행렬곱은 기존 translation도 회전시키지만 여기서는 그렇지 않다. 18절의 기구학 world-motion 합성은 별도의 식이다.

연습: R=I, t=(0.1,0,1)이고 mesh 점이 (0.02,0,0)이라면?

카메라 점은 (0.12,0,1)m다. fx=600, cx=320이면 u=392px다. “mesh 위치”와 “camera 위치”를 구분해서 계산하는 것이 목표다.

코드 대응: geometry.py의 transform/axis_angle_matrix/decode_pose, omy_sequence.py의 target, visualization.py의 project_segments. 예제 수치는 설명용이며 실제 카메라 calibration이 아니다.

23 · Loss와 gradient: 숫자로 따라가는 학습

학습은 입력을 보고 출력하는 함수의 내부 숫자 θ를, 정답과의 오차가 줄어드는 방향으로 조금씩 바꾸는 과정이다.

입력·정답·파라미터는 서로 다르다

prediction = fθ(input)에서 θ는 Linear/attention 등의 weight와 bias다. 이미지, 관절각, 시작 pose는 매 sample 달라지는 입력이다. 정답 pose는 loss를 계산할 때 비교하는 값이다. 입력 관절각 자체를 optimizer가 수정하는 것이 아니다. 처음부터 모든 weight를 무작위로 시작하는 대신, 우리는 이미 학습된 visual encoder와 pose heads를 가져오고 새 geometry encoder/fusion을 초기화한다.

미분을 손으로 따라가는 작은 예제

원리를 위해 입력 x=2, 정답 y=1, 모델 ŷ=wx, 초기 weight w=0, 손실 L=½(ŷ−y)²로 단순화하자. 이것은 실제 pose loss나 AdamW가 아닌 단일 weight의 SGD 학습 예제다.

Forward:  ŷ = 0×2 = 0
Loss:     L = ½(0−1)² = 0.5
Gradient: dL/dw = (ŷ−y) × x = −2
Update:   w_new = w − η·dL/dw
η=0.1이면 w_new=0.2 → 새 ŷ=0.4 → 새 L=0.18

Gradient가 음수라는 것은 w를 조금 증가시키면 loss가 작아지는 방향이라는 뜻이다. Gradient descent는 gradient를 더하지 않고 뺀다. 여러 층에서는 dL/dw = (dL/dŷ) · (dŷ/dw)처럼 미분을 연결하는 chain rule을 반복한다. backward()가 이 계산을 수행하고, optimizer.step()이 실제 weight를 바꾼다.

한 번의 업데이트 전후를 계산한다. 우리 모델의 적정 lr을 추천하는 도구가 아니다. 같은 0.1도 이 예제에서는 유효하지만 실제 네트워크에서는 지나치게 클 수 있다.

η=0이면 변화가 없고, η=0.25이면 이 단순 예제는 한 번에 정답에 도달한다. η=0.6이면 오차가 커진다. 실제 비선형 네트워크에서는 batch, loss의 단위, optimizer에 따라 변화가 달라지므로 “큰 lr이 빠르다”로 일반화할 수 없다.

실제 pose loss는 어떤 오차를 줄이나

L_batch = (1/B) Σ_b min_s [(1/N) Σ_i || T_pred,b p_i − T_gt,b S_s p_i ||₂]
B: batch sample 수, N: CAD점 수, S_s: 선언된 대칭변환

학습에서는 N=256이다. 각 sample에서 CAD 표면점의 Euclidean 거리를 평균하고, 선언된 대칭이 있으면 그중 최소를 고른 뒤 batch를 평균한다. 위치와 회전의 오차가 모두 이 거리에 반영된다. 반지름 5cm인 점이 그 원점을 중심으로 10° 돌아가면 이동 거리는 2×0.05×sin(5°) ≈ 8.72mm다. 원점의 translation error가 0이어도 surface error는 0이 아닐 수 있다.

이 예제의 제곱오차와 실제 평균 Euclidean 거리 loss는 다른 함수다. 출력 logits에 별도 “정답 correction”을 직접 맞추는 것이 아니라, correction을 pose로 decode한 결과의 표면 오차로 학습한다. 평가 rollout은 별도 seed의 4,096점을 사용한다. 대칭을 선언하지 않으면 코드가 자동으로 대칭성을 찾아주지는 않는다.

실제 optimizer와 학습 모드

현재는 AdamW를 사용한다. gradient의 1차·2차 이동평균과 bias correction으로 각 파라미터의 업데이트를 조절하고, weight decay를 분리 적용한다. 코드가 기본값을 생략한 부분은 PyTorch 2.8 기준 betas=(0.9, 0.999), eps=1e-8, weight_decay=0.01이다. 즉 “weight decay를 쓰지 않는다”는 설명은 틀리다. 우리 학습률은 별도로 새 모듈 1e-4, heads 1e-5로 지정한다. AdamW 공식 문서.

일반 SGD 예제의 update 식을 AdamW의 정확한 계산식으로 받아들이지 말자. Gradient clipping의 1.0은 pose 오차 1m를 제한하는 값이 아니라 전체 gradient norm의 상한이다. lr scheduler, 자동 early stopping, AMP, 여러 프레임을 관통하는 역전파는 현재 trainer에 없다. --warmup-epochs는 learning rate를 서서히 올리는 설정이 아니라 heads를 고정하는 epoch 수다.

설정하는 일하지 않는 일
requires_grad=False그 parameter의 gradient/업데이트를 막는다.해당 연산을 통한 입력 gradient를 반드시 끊는 것은 아니다.
no_grad()블록 내부 연산의 autograd 기록을 끈다.Dropout을 자동으로 끄지 않는다.
model.eval()Dropout/BatchNorm 등 모듈의 평가 동작을 선택한다.Gradient 계산을 자동으로 끄지 않는다.

이 구분은 PyTorch autograd 문서와 일치한다. 실제 trainer는 validation에서 eval과 no_grad를 함께 사용한다. Tiny의 heads는 weight가 고정돼도 model.train() 상태이므로 dropout=0.1이 켜져 있다. 따라서 Tiny train loss가 매 step 완전히 일정하거나 매번 감소해야 하는 것은 아니다. Fusion cross-attention의 dropout은 0이다. Head 구조의 기본값은 TransformerEncoderLayer 문서에서도 확인할 수 있다.

연습: backward()만 하고 step()을 하지 않으면?

Gradient는 생기지만 weight는 업데이트되지 않는다. 반대로 zero_grad를 빠뜨리면 gradient가 누적된다. 현재 코드는 batch마다 zero_grad → forward/loss → backward → clip → step을 수행한다.

24 · Encoder와 attention을 코드에 연결하기

Encoder는 입력을 비교하기 좋은 특징으로 바꾸고, fusion은 그 특징들을 섞고, head는 특징을 최종 출력 숫자로 바꾼다. 세 이름은 역할을 구분하는 말이다.

Feature와 token은 무엇인가

Feature는 모델이 학습한 특징 숫자다. “이 숫자는 반드시 손가락, 저 숫자는 접촉”처럼 사람이 의미를 지정하지 않는다. Token은 특징 벡터 하나다. Visual token은 이미지 특징 맵의 한 공간 위치에서 나오지만, CNN의 receptive field 때문에 딱 한 pixel만 표현하지 않는다. Geometry token은 여러 3D 이웃 점을 모아 만든다.

CNN은 작은 공간 필터를 여러 위치에 공유해 이미지 패턴을 처리한다. MLP는 Wx+b 형태의 Linear 연산과 비선형 함수를 여러 층 쌓은 네트워크다. 비선형 함수 없이 Linear만 여러 번 쌓으면 결국 하나의 Linear로 합쳐진다. 여기서는 GELU를 사용한다. LayerNorm은 특징 벡터의 크기 분포를 정리하고 학습 가능한 scale/bias를 적용한다. 3D 좌표를 물체 diameter로 나누는 기하 정규화와는 다른 연산이다.

위치 embedding은 특징만으로 구분하기 어려운 위치 정보를 더한다. Visual 쪽은 upstream의 고정 sinusoidal embedding이고, geometry 쪽은 중심점 XYZ를 작은 MLP로 바꾼 학습 가능한 embedding이다. 표의 max pooling은 각 feature 채널에서 이웃들의 최대값을 뽑는 연산이다. 물체 pose의 최댓값을 고르는 것이 아니다.

흐름기본 shape코드에서 하는 일
각 렌더/관측 crop[B, 6, H, W]RGB 3 + XYZ 3. 현재 bridge는 normal 입력을 지원하지 않는다. 사용할 upstream config의 c_in도 이 입력과 맞아야 한다.
Frozen visual[B, L, 512]두 crop을 shared encodeA로 처리하고, 채널 결합 → encodeAB → 위치 embedding.
Robot + CAD 입력[B, 768, 11]로봇 512점 + 물체 CAD 256점. 11개 채널은 05절 참조.
Local aggregation 1128개 중심, 특징 64공간적으로 퍼진 중심점을 선택하고, 가까운 최대 16개 중 반경 0.15 이내를 사용.
Local aggregation 232개 중심, 특징 128반경 0.35로 다시 이웃을 모은다. 반경은 diameter로 나눈 좌표의 값이다.
Geometry token[B, 32, 512]128→512 projection + 중심점 좌표의 학습된 embedding.
Fusion / heads[B,L,512] → [B,3] 각각Cross-attention residual → trans/rot heads → token 축 평균.

실제 입력점 수가 기본값보다 작으면 중심점 수도 줄어든다. Point aggregation은 상대 좌표와 기존 feature를 MLP에 통과시키고 채널별 max를 취한다. 서로 다른 채널의 최대값이 서로 다른 이웃에서 나올 수 있다. Sampling/grouping으로 “학습 가능한 점 좌표”를 새로 생성하는 구조는 아니다.

이 계층적 local aggregation은 PointNet++에서 영감을 받았지만, 우리 코드는 nearest-neighbor + radius mask, LayerNorm/GELU 등을 사용한 자체 구현이다. 논문의 전체 모델이나 multi-scale grouping을 그대로 재현했다고 주장하지 않는다.

중요한 구분: 이름은 RobotEncoder지만 32개 token에는 로봇점과 물체 CAD점이 함께 들어간다. “32개 robot link token”도 “관절 32개”도 아니다. 성능 개선을 robot state만의 효과라고 말하려면 CAD-only 비교가 추가로 필요하다.

Cross-attention을 숫자로 이해하기

Q = LayerNorm(visual) · Wq
K = LayerNorm(geometry_tokens) · Wk
V = LayerNorm(geometry_tokens) · Wv

A = softmax(QKᵀ / sqrt(d_head))
extra = concat(head_1, ..., head_4) · Wo
fused = visual + alpha · extra

위 식은 projection bias를 생략한 설명이다. Query는 “현재 시각 특징이 무엇을 참고할까”, Key는 매칭할 특징, Value는 가져올 정보 역할이다. 우리 모델은 512차원을 4개 attention head로 나누므로 head당 128차원이다. 각 visual token은 32개 geometry token에 대한 가중치를 계산한다. 여기서 attention head 4개와 translation/rotation 출력 head 2개는 다른 뜻이다.

예를 들어 두 key에 대한 정규화 전 점수가 [2,0]이라면 softmax 가중치는 약 [0.881,0.119]다. 이것은 key 두 개를 비교하는 설명용 예제다. 실제 입력은 기본 32개이고 점수도 학습된 projection에서 나온다. 가중치가 높다고 그 token이 물리적 접촉 원인임이 증명되지는 않는다. 연산의 일반 원리는 Attention Is All You Need 3.2절에서 확인할 수 있다.

Key가 하나뿐인 일반 softmax attention은 그 key의 가중치가 항상 1이라 query에 따른 선택이 사라진다. 여러 local token을 쓰는 이유 중 하나다. 다만 token 수가 많을수록 정확도가 좋아진다는 보장은 없다.

alpha는 처음 0.01인 모든 sample이 공유하는 scalar parameter다. 접촉 여부에 따라 매 프레임 달라지는 trust gate가 아니고 확률도 아니다. 초기에는 visual 특징에 작은 보정을 더하자는 설계지만, 실제 보정량은 extra의 크기에도 달려 있다. alpha=0으로 만들면 유한한 입력에서 출력 residual은 사라지지만 branch 계산은 수행한다. bypass/visual 모드는 branch 자체를 건너뛴다.

모드는 네 가지다. visual: branch를 건너뛰고 pose heads만 학습. cad-only: is_robot=0인 CAD 행(256개)만 같은 encoder·fusion에 넣는다. 로봇 행은 0으로 만들거나 채우지 않고 아예 뺀다. CAD 점은 물체 자기 좌표계 값이라 위치 정보 없이 물체 형상만 전달하므로, “branch를 붙인 효과·물체 조건화”와 “로봇 정보”를 나누는 대조군이다. geometry: 로봇 512 + CAD 256점, 속도·validity 0. motion: 모든 채널.

학습되는 크기와 아직 없는 것

현재 기본 구조를 CachedHeads로 구성해 센 parameter 수는 새 encoder/fusion 1,413,953개, 두 pose heads 3,159,046개다. Frozen visual encoder는 이 수에 포함하지 않았다. Tiny에서는 새 부분만, geometry/motion pilot에서는 둘 다 업데이트한다. Visual-only에서는 pose heads만 loss에 연결돼 업데이트된다. 이 숫자는 실행 시간이나 VRAM 측정값이 아니다.

Motion 입력은 현재·직전 관절 위치로 얻은 표면점의 유한차분 속도다. 관측 파일의 joint_velocities를 그대로 넣는 것이 아니다. 현재 모델에는 이전 RGB를 보는 encoder, recurrent memory, sequence Transformer, contact probability 출력이 없다. 이전 prediction을 다음 frame의 hypothesis로 전달하는 tracker의 외부 상태는 있지만, neural network 내부가 긴 sequence를 학습하는 것은 아니다.

FoundationPose는 본래 CAD 또는 reference images 조건의 novel-object pose 추정/추적을 다룬다. 우리는 그중 CAD가 있는 조건의 pretrained refiner를 사용하고 일부 모듈을 추가 학습한다. 원 논문의 전체 학습 절차·scoring 학습을 재현하거나, 현재 pilot만으로 novel-object 일반화를 입증한 것은 아니다. FoundationPose 원 논문.

연습: 이 모델의 alpha를 보고 “지금 grasp했을 확률”이라고 해석해도 될까?

안 된다. alpha는 현재 입력에 따라 생성되는 확률이 아니라 학습된 전역 scalar다. Attention 결과 extra는 입력에 따라 달라지지만, 이것도 contact 확률로 학습된 값은 아니다.

25 · 처음 학습할 때의 관문과 파일 읽기

처음 실행할 때의 목표는 최고 성능이 아니라, 입력·출력·학습·평가가 올바르게 이어지는지 확인하는 것이다. 아래 관문을 통과한 뒤 다음 단계로 간다.

명령어를 읽기 위한 최소 지식

모든 명령은 저장소 최상위, 즉 scripts/와 docs/가 보이는 디렉터리에서 실행한다. python은 현재 활성화한 환경의 Python이다. python -m pip는 그 Python에 패키지를 설치한다. 가상환경 이름은 각 컴퓨터에서 다르므로 문서가 임의로 활성화해주지 않는다.

export OMY_WORK="..."는 해당 terminal session에서 쓸 경로 변수다. 새 terminal에서는 다시 설정해야 한다. $PWD는 현재 디렉터리이며 코드 저장소에서 지정해야 의도한 output 경로가 된다. 예시의 /home/a09/...는 본인 머신의 실제 경로로 바꾼다. 줄 끝의 \는 다음 줄까지 한 명령이라는 뜻이고, 그 뒤에 공백을 붙이지 않는다. --execute 없이 계획만 출력하는 것은 run_omy_training/run_omy_comparison의 기능이며, 모든 scripts에 통하는 규칙은 아니다.

현재 안내는 Linux + 작동하는 FoundationPose CUDA 환경을 전제로 한다. Windows native/WSL에서의 실행은 이 브랜치로 검증하지 않았다. 이 HTML은 5080 환경 자동 설치기나 호환성 보증이 아니다. CUDA tensor 연산이 성공해도 renderer/native extension이 실패할 수 있어서 smoke가 필요하다.

생성되는 파일을 잃지 않기

cache/heads.pt는 원본 pretrained heads의 출발 weight이고, run-.../best.pt는 학습 결과다. 이름이 비슷해도 역할이 다르다. Cache의 각 sample .pt에는 정답도 들어 있으므로 추론 관측 파일처럼 취급하지 않는다.

학습 checkpoint에는 새 모듈과 pose heads, optimizer, epoch, best loss, config, train provenance, torch RNG 상태가 들어간다. Frozen visual encoder의 weight는 들어 있지 않다. 실제 RGB-D 추론에는 pinned FoundationPose 코드와 원본 pretrained weights가 여전히 필요하며, 저장된 weight hash와 같아야 한다. Checkpoint 파일 한 개를 복사했다고 독립 실행 모델이 완성되지는 않는다.

best.pt는 cache의 one-step validation loss가 가장 낮았던 시점, last.pt는 마지막 완료 epoch다. Tracker 성능의 best는 rollout으로 따로 판단한다. Resume의 --epochs 40은 40번을 추가한다는 뜻이 아니라 전체 epoch index 0~39까지 진행한다는 뜻이다. Optimizer state를 복원하므로 CLI의 새 lr/head-lr가 자동으로 적용되는 설정 변경용 경로도 아니다. 같은 cache/mode/batch/warmup 설정을 유지한다.

Ctrl+C는 현재 epoch 중간 상태를 저장해주지 않는다. 완료된 checkpoint부터 새 output 디렉터리에서 재개한다. 현재 실행기에는 이미 완료한 stage를 자동으로 찾아 건너뛰는 resume 기능이 없다. HTML 10절과 19절에 중복된 명령을 두 번 실행하지 말고 완료한 단계는 넘어간다.

실험 기록과 지표를 해석하기

실제로 동작한 환경에서는 python -m pip freeze > "$OMY_WORK/environment.txt", nvidia-smi > "$OMY_WORK/gpu.txt", git rev-parse HEAD > "$OMY_WORK/code_commit.txt"를 기록할 수 있다. work가 생성된 뒤 실행하며 이 기록 자체가 완전한 환경 재현이나 성능 측정은 아니다.

Train loss는 epoch 도중 바뀌는 weight와 활성 dropout으로 계산되고, validation loss는 epoch 끝 weight와 eval 모드로 계산된다. 그러므로 validation이 train보다 작다는 것만으로 leakage라고 단정할 수 없다. 같은 물리 rollout이 split 사이에 섞이는 문제는 별도로 검사한다.

Loss가 줄어도 unseen sequence의 tracking이 좋아졌다는 뜻은 아니다. Train은 fitting, validation은 설정 선택, test는 선택 후 독립 측정이다. 현재 validation을 보고 반복해서 고른 결과는 독립 test가 아니다. 9개 clip의 macro 평균은 긴 clip에 가중하지 않지만 B/C가 같은 physical parent일 수 있어 표본 9개가 모두 독립인 것도 아니다.

26 · 공부 순서와 정확성 검토 기록

이론을 모두 공부한 다음 시작할 필요는 없다. 각 단원을 읽고 작은 계산이나 코드 한 구간을 설명할 수 있는지 확인한 뒤 다음으로 넘어가자.

학습 순서읽을 곳이해했다고 볼 기준
1. 문제와 데이터01~03, 06절우리가 로봇 policy나 object detector 전체를 학습하는 것이 아니라 pose refiner를 학습함을 설명한다. Input과 GT를 구분한다.
2. 좌표·기하22절 → 05, 18절mesh 점을 camera로 옮기고 pixel로 투영한다. velocity에는 translation을 더하지 않는 이유를 설명한다.
3. 학습 원리23절 → 07~09절forward, loss, backward, step의 차이를 설명하고 scalar 예제의 gradient를 계산한다.
4. 실제 아키텍처24절 → 04, 11절[B,768,11]에서 [B,32,512]까지의 의미, Q/K/V의 출처, frozen 경계를 설명한다.
5. 첫 실행25절 → 10, 19, 21절단계별 출력 파일과 다음 단계로 넘어갈 근거를 확인한다. 실행 명령을 무조건 전부 반복하지 않는다.
6. 연구 판단12~13, 20절원본 대비 개선과 robot 정보의 이득을 구분하고, 간단한 baseline이 충분할 가능성도 평가한다.

논문·공식 문서는 무엇을 확인하며 읽을까

Modern Robotics 3.3.1에서는 좌표 변환의 곱셈 순서를 확인한다. PyTorch autograd에서는 requires_grad/no_grad/eval의 차이를 확인한다. AdamW에서는 우리 trainer가 생략한 기본 설정과 optimizer state를 확인한다.

PointNet++에서는 왜 전체 point cloud를 한 번에 요약하지 않고 local 영역을 단계적으로 모으는지 본다. Attention 논문 3.2절에서는 Q/K/V와 softmax 식을 이해한다. FoundationPose에서는 registration, refinement, tracking의 관계와 model-based/model-free 조건을 구분한다. 먼저 필요한 부분부터 읽고 실험 표 전체를 외우려 하지 않아도 된다.

일반 이론의 근거는 위 문헌이고, “우리 모델의 token 수·학습률·freeze 방식·출력 파일”의 기준은 해당 브랜치 코드다. PyTorch 2.8 문서는 이번 CPU 검증 환경과 맞춰 확인한 버전이며 5080 환경을 2.8로 강제 설치하라는 뜻은 아니다. 데이터 규모는 저장소의 pinned pilot manifest를 기준으로 계산했다.

이번 정확성 검토에서 명확히 고친 부분

  • RobotEncoder의 32개 token에는 robot와 object CAD가 함께 들어간다. 순수 robot-only 표현으로 설명하지 않는다.
  • Tiny heads의 weight freeze와 eval 모드를 구분했다. Train 중 head dropout은 켜져 있다.
  • Motion은 local state의 유한차분 속도 입력이다. 긴 sequence를 보는 neural memory나 GT contact gate는 없다.
  • Tiny → pilot → motion은 실험 순서다. 이전 단계의 checkpoint를 자동으로 이어받지 않는다.
  • best.pt는 frozen visual encoder를 포함하지 않으며 one-step 기준으로 선정된다.
  • 기존 본문의 최대 sample 수·geometry 규약·oracle 초기화 예외·독립 test 부재를 현재 코드와 대조했다.

이 검토는 학습 성공을 새로 실측한 것이 아니다. 실제 데이터 checksum, calibration/영상 정합, 5080 renderer 호환성, loss 감소, baseline 대비 성능 향상은 실행 결과가 필요하다. 문서에서 “이론으로 기대하는 효과”, “코드로 구현된 동작”, “실험으로 확인한 사실”을 서로 바꾸어 읽지 않는 것이 중요하다.

종합 문제 1: 원본보다 좋아졌고 visual-ft와는 같다면 무엇을 주장할 수 있나?

추가 학습의 이득일 수 있다. Robot 정보를 넣었기 때문이라고 결론내리기에는 증거가 부족하다. 같은 cache·heads 일정의 visual control과 비교하는 이유다.

종합 문제 2: 기구학 prior가 B에서는 좋고 A/C에서는 나쁘다면?

항상 rigid grasp라는 가정이 특정 구간에서만 맞는다는 설명과 일치할 수 있다. 먼저 영상과 구간별 오차로 확인한다. 다음 연구 후보는 관측으로 prior의 신뢰도를 판단하는 모델이지만, 이번 구현에 그런 gate가 이미 있는 것은 아니다.

종합 문제 3: Tiny loss가 줄었으니 바로 논문 성능표를 만들어도 될까?

아니다. Tiny는 fitting/gradient 경로 진단이다. 같은 초기화의 validation rollout과 baseline을 비교하고, 최종 주장에는 별도의 test rollout이 필요하다.
